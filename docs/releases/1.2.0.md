# OIE Sentinel 1.2.0

Release for **OIE 4.6.0** with notification, monitoring, configuration import, and dashboard correctness fixes. The supported engine range remains exactly 4.6.0.

## Changes

- Monitoring reads and dry runs respect authorized channel scope, including monitor dependencies and group, tag, and user metadata. Configuration management grants remain global.
- Configuration imports that include schedules require **Manage Schedules** before any import writes begin.
- Webhook URLs, bodies, and header values are encrypted on write and masked on configuration reads. Masked edits preserve existing credentials; legacy stored values remain readable by 1.2.0.
- Pending notifications revalidate action definitions before transport, including escalation sources. Edits to recipients, credentials, conditions, or delivery phases defer or cancel stale work without losing eligible recovery notifications.
- Inactivity, low-volume, and anomaly monitors require sufficient successful sample coverage. Missing telemetry preserves open incidents instead of treating an unobserved interval as measured zero. Coverage, aggregates, and anomaly baselines are read consistently during concurrent collection and retention.
- Export/import preserves monitor identity and recipient routing, rejects ambiguous names, and keeps dependents from using monitor definitions rejected by the same import. Independent valid entries can still import; inspect the per-entry result before retrying. Export format 3 is readable by 1.2.0; older format 1 and 2 imports remain supported.
- Rapid enabled-state changes for one maintenance window execute in order. A failed request cancels queued changes for that window; check its saved state before retrying an uncertain timeout. Other windows remain independently usable.
- Storm rollups apply recipient routing rules and release reservations when subject lookup fails. Recovery notification ceilings use dispatch time.
- Connector observation retries preserve deployment and telemetry certainty. Interrupted schedule migrations and incomplete hourly rollups can recover without silently losing totals.
- Dashboard badges expose incomplete or stale data, activity charts stay associated with their selected channel, and background refreshes no longer strand the problem list in a loading state.

## Upgrading

**Stop Sentinel on every cluster node before starting 1.2.0 on any node. Install the same version on every node before monitoring resumes.** A rolling mixed-version upgrade is not supported.

1. Stop Sentinel on all nodes and prevent configuration writes during the backup and upgrade. Take a consistent backup of the engine database, including Sentinel tables, and retain the matching engine encryption/keystore material and previous plugin archive. A configuration export masks credentials and is not a substitute for this backup.
2. Install 1.2.0 over the existing extension on every node; do not uninstall as an upgrade step. Restart the engines only after all nodes have the updated archive.
3. The database schema migrates automatically from version 12 (1.1.2) to version 13. Confirm successful migration, one active monitoring leader, fresh collector samples, expected channel visibility, and notification routing before returning the deployment to service. Inspect import results for rejected entries instead of assuming an entire document succeeded.

New webhook writes use the `sentinel-secret:v1:` encoding for sensitive values. The 1.2.0 sender reads legacy values, but the 1.1.2 sender expects plaintext URL/body values and cannot use these new writes. Shared database access does not make old and new senders compatible.

### Rollback

Stop Sentinel on every node before a rollback. Restore the coordinated pre-upgrade database backup and its matching encryption material, install the previous plugin version on every node, and restart together. This restores the backed-up state and discards changes made after that backup. Downgrading only the plugin against the upgraded or edited database is not a supported rollback procedure. Do not uninstall to roll back: uninstall archives Sentinel tables rather than restoring the prior schema.

## Release validation

Before publishing, validate the final merged commit and its 1.2.0 archive, including the supported-database upgrade checks and the coordinated cluster procedure. Verify the signed draft asset, its SHA-256 checksum, and build provenance. Local builds and offline signing tests do not establish that the production signing service or a live cluster upgrade has passed.

Notification delivery remains at least once: a crash after external delivery but before its dispatch-log commit can duplicate a notification on retry. Schedule ordering applies within an open schedule page; separate clients or reopened pages can still issue concurrent edits.
